# Gotchas

_Things that have bitten us or are easy to get wrong. Updated in place._

- **Never subtract timestamps from two different machines.** Server delay = `stored_at − received_at`. Client round-trip = generator's own clock. Report baseline `ping` separately.
- **Never commit `.env`, certs, or private keys.** Use `.env.example` as the template.
- **Duplicate `(device_id, seq)` is not an error** — return 200, not 4xx (MQTT QoS 1 can redeliver).
- **AWS region is always `us-east-1`** — cost model is priced there.
- **`received_at` and `stored_at` both come from the app clock, never Postgres `now()`.** At Stage C the DB is on RDS, a different machine.
- **`stored_at` is briefly `NULL`.** It is set by a second `UPDATE` after the insert commits. Downtime and delay queries must ignore `NULL`. A row keeps `NULL` for good only if the database fails between the insert and that `UPDATE`: the SQS retry then sees a duplicate and does not repair it. After the load has stopped and the queue is empty, count `stored_at IS NULL` to flag such rows.
- **Seed `patients` before any reading.** `readings.patient_ref` is a foreign key; an unseeded code is rejected (HTTP 422).
- **B→C: restore first, then start the app.** If the app starts against an empty RDS it creates the tables, and `pg_restore` then clashes with them.
- **`paho-mqtt` is pinned `<2`** (v1.x callback API). Write MQTT code in that style.
- **The MQTT worker uses a persistent session** (fixed client ID `healthsuite-worker`, `clean_session=False`), so Mosquitto queues QoS 1 messages while it is down (checked: 5 messages sent while the worker was stopped were all stored after restart). Run only **one** worker per client ID; a second one with the same ID kicks the first off.
- **paho-mqtt 1.6.1 allows only 20 in-flight QoS 1 messages by default** (checked on the client object). At a 200–250 ms round trip that caps one connection at roughly 80–100 msg/s; the generator must call `max_inflight_messages_set()` and probably use several connections.
- **MQTT mode: an error inside `process` (for example the database being down) is logged and the message is still acked, so that reading is lost.** Only the worker's loop is protected, not the reading. Count this as lost readings in any outage test. SQS mode (Stage C) differs on purpose: invalid readings and unknown patients are deleted, but any other error leaves the message in the queue and SQS redelivers it after the 30 s visibility timeout, so a database outage loses nothing. There is no dead-letter queue because a low receive count would also move readings away during a long outage; a message that always fails unexpectedly would loop until the 4-day retention ends.
- **Laptop Python is 3.14; containers use 3.12.** Some packages may lack 3.14 builds, so run tests in a 3.12 venv.
- **Stage C server time excludes the SQS wait.** `received_at` is stamped by the worker, after the queue. The wait is not measured per message: the measured-run script samples the queue depth every 5 s (`GetQueueAttributes`, counts are approximate) and waits for it to drain, which gives the backlog curve and the time to drain. At 10 and 100 msg/s the wait is too small for that to resolve.
- **Database URLs must say `postgresql+psycopg2://`.** A bare `postgresql://` makes SQLAlchemy 2.1 look for psycopg v3 and the app crashes with `No module named 'psycopg'` (checked with SQLAlchemy 2.1.8, which `requirements.txt` resolves to). Compose already builds the right URL; the `DATABASE_URL` in `.env.example` is still the bare form.
- **A database connection that the server dropped can freeze a process.** Seen on Stage C (2026-11-14): the worker sat in the pool's health check (`pool_pre_ping`, `do_ping`) on a dead RDS connection, so it stopped taking messages while the container looked "Up", and the SQS test messages stayed in the queue. Without timeouts the wait is bounded only by the kernel's TCP retry limit (about 15 minutes, not measured here). `app/db.py` now passes libpq options (`connect_timeout` 10 s, TCP keepalives, `tcp_user_timeout` 30 s) so a dead connection fails in about a minute. Diagnose a "Up but idle" worker with a `py-spy dump` of its process; `docker restart infra-worker-1` clears it. The messages it had not stored are stored after the restart, so clean up leaked `it-` rows (see the integration-tests gotcha).
- **Run Compose from the repo root with `--env-file .env`** (`docker compose --env-file .env -f infra/docker-compose.yml up --build`), otherwise `${POSTGRES_*}` is read from `infra/` and Compose fails with "set POSTGRES_… in .env".
- **A local PostgreSQL on the laptop usually already owns port 5432.** Set `POSTGRES_HOST_PORT` (for example 5433) in `.env`; containers still talk to each other on 5432.
- **Mosquitto queues at most 1000 messages per client by default** (its documented default, not measured here). `infra/mosquitto/mosquitto.conf` raises it to 100000, because the 20 s restart test at 100 msg/s queues about 2000.

- **Locust's `FastHttpUser` allows only 10 concurrent connections by default** (`concurrency`, read from its source). At a 200-250 ms round trip that would silently turn the open-loop generator into a closed loop at about 40-50 msg/s; `loadtest/locustfile.py` sets the pool to 2 x rate.
- **paho-mqtt calls `on_publish` while holding its own lock** (read from the 1.6.1 source), so calling `publish()` while holding a lock that `on_publish` also needs deadlocks. `loadtest/mqtt_generator.py` registers a message only after `publish()` returns and keeps a PUBACK that arrives before that.
- **paho-mqtt 1.6.1 keeps a QoS 1 message published while disconnected** (`publish()` returns `MQTT_ERR_NO_CONN` but the message stays queued) and sends it after the reconnect; the generator logs it as `error` and ignores the late PUBACK. Packet ids wrap at 65535 per connection, so pending messages are keyed by (connection, id).
- **The MQTT generator's `ok` is the broker's PUBACK, not "the database stored it".** It covers only generator to broker; the worker acks to the broker separately after the insert. Check stored row counts against `ok` after every run.
- **Integration tests write to the real database.** Rows use `device_id` starting `it-` and are deleted at the end of the run, but do not run them during a measured run or while counting rows for the B to C migration check. If a run is killed, or the worker is down so an MQTT test fails, the broker still holds the message and the worker stores it after the cleanup (seen: 2 leaked rows), so clean up with `DELETE FROM readings WHERE device_id LIKE 'it-%'`. On Stage C a leaked test message waits in the queue for up to 4 days and is stored whenever the worker next runs, so purge the queue and count `it-` rows before a measured run or the migration check.
- **Integration tests need the app's packages, not only pytest.** `tests/conftest.py` imports `app.rules` (pydantic), and `tests/integration/live.py` needs `httpx` (only in `requirements-dev.txt`). In a bare `python:3.12-slim` container (how they run on the VM), install `-r requirements.txt pytest httpx`; with fewer packages pytest stops at collection with `ModuleNotFoundError` (seen: `pydantic`, then `httpx`).
- **A second `conftest.py` without an `__init__.py` shadows `tests/conftest.py`** and breaks every `from conftest import ...` (seen when adding `tests/integration`). That directory is a package for this reason; import its helpers as `from integration.live import ...`.
- **The baseline ping needs a target that answers ICMP.** From the Oracle box, `ec2.us-east-1.amazonaws.com` (the AWS API endpoint, not our VM) showed 100% loss, so do not use it. Stage B: the VM's security group must allow ICMP echo from the Oracle IP, or `ping.txt` just says "ping failed or is blocked" and the run goes on without a baseline. Stage C: the IoT Core endpoint probably will not answer ICMP (not tested yet); if so, record a TCP connect time to its port instead and say which method each baseline used. The same applies to a laptop behind NAT in Stage A.
- **`ping` inside the generator container needs `cap_net_raw`.** The Oracle host has `net.ipv4.ping_group_range = 1 0` (unprivileged ICMP off) and the Debian 13 `iputils-ping` package no longer sets the capability, so `loadtest/Dockerfile` runs `setcap cap_net_raw+ep /usr/bin/ping`. Without it, `--user` runs fail to ping.
- **`rsync --delete` from `loadtest/` removes any file that exists only on the Oracle box.** Keep everything the box needs (including `loadtest/Dockerfile`) in the repo.
- **Tailscale: log in with a personal account, in a private browser window.** Signing in with a university Google account put the laptop in the university's tailnet (`dau.ac.in`), where an admin must approve devices, and Chrome then kept that session and blocked the personal login ("while you were logged into tailnet dau.ac.in..."). Use an incognito window.
- **The Tailscale container must not use its default login mode.** The image's start script gives up after about 60 seconds waiting for a browser login, exits and restarts with a new link and no saved login. Run it as `--entrypoint tailscaled --state=/var/lib/tailscale/tailscaled.state`, then `docker exec it457-tailscale tailscale up --accept-dns=false --hostname=it457-loadgen` (no time limit).
- **Check the laptop's Wi-Fi before every measured run.** Ping the router (want about 2-5 ms, max under 10) and look at `iw dev wlo1 link` (signal better than -65 dBm, 5 GHz). On 2.4 GHz at -72 dBm the router ping averaged 61 ms with spikes to 274 ms, and it dropped to -80 dBm (spikes to 361 ms) when the laptop was moved. Server time is unaffected, but the client round trip and arrival bursts are not. Keep the laptop in the same spot, plugged in, for every run.
- **With `BIND_IP` set, `localhost:8000` stops answering** (the ports are published on the Tailscale address only). Use that address for local checks. If Tailscale is down when Compose starts, the bind fails.
- **Smoke tests use stage `smoke`**, because a run tag like `ah10r1` would collide on `UNIQUE (device_id, seq)` with a later measured run using the same tag. The smoke rows stay in the database (`device_id LIKE 'smoke%'`).
- **One MQTT connection adds about 20 ms to the client round trip once the rate is 50 msg/s or more.** Stage A, MQTT, 1 connection: median 27-36 ms; the same run with 100 connections (one per device): median 13.7-15.5 ms; HTTP about 16 ms. Server time did not change. Cause not isolated (likely small-packet batching on the single TCP stream). Measured MQTT runs use `CONNECTIONS=100` (`A_mqtt-100conn_*`); the 24 first-matrix runs (`A_http_*`, `A_mqtt-1conn_*`) are kept as a labelled side result. The MQTT round trip also ends at the broker's PUBACK, before the database save, unlike HTTP.
- **Turn Wi-Fi power save off on the laptop before a measured run** (`iw dev wlo1 get power_save`; `sudo iw dev wlo1 set power_save off`, resets on reboot). With it on, a 1-per-second `ping` read 50-60 ms on average (fastest packet 13.6 ms) because the idle radio sleeps between packets; the preflight pings every 0.2 s and does not notice. That inflated `ping_avg_ms` in the notes of most `A_mqtt-100conn_*` runs (39-85 ms); their client round trip (generator clock) is unaffected, so use the fastest ping or the `A_http_*` runs' baseline for those.
- **The lost-readings formula cannot see losses at the end of a device's sequence.** `(max(seq) - min(seq) + 1) - count(distinct seq)` only counts gaps between stored readings; in `A_http_50per-s_run1` one final reading was lost and the formula said 0. Also report `missing` = sent - stored (`measure_run.sh` records it; `results/run_stats.csv` has it for every run). For HTTP, a request that failed with a connection error counts as missing.
- **`docker compose stop worker` takes 10 s and then kills the worker.** It does not react to the stop signal (it kept storing for 10.2 s every time), so a restart or deploy force-kills it; the broker redelivers the unacknowledged message and the duplicate is ignored. The restart test measures the outage from when `stop` returns (about 21 s gap for a 20 s stop).
- **The run folder date is the Oracle container's UTC date**, not local time, so a run late in the evening can carry another day's date than the laptop clock.
- **Stages A and B use plain HTTP and plain MQTT (port 1883, anonymous).** AWS IoT Core accepts MQTT only over TLS (8883, device certificate), so Stage C round trips include TLS and are not directly comparable with A and B on that point; say so in the report. Tailscale encrypts the A path for both protocols equally.
